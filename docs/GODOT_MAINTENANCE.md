# Godot 版与 Web 版的差异，以及 AI 维护规范

更新：2026-10-04。适用项目：`/Users/yunni/Joy/inkwave-game-cleaned`，Godot 4.8.dev6，Apple Silicon / arm64。入口在根目录 `project.godot`。

本项目已经独立维护。当前工作树不包含 Web 页面、服务器、浏览器测试、JavaScript 转换器、Three.js 模块、Node 包或网页构建配置。Godot 源码、资源、检查与导出均不读取旧项目。Git 早期提交与部分历史文档／资源清单仍记录移植来源；这些记录不作为当前可执行流程。

## 1. 差异对照与边界

对照来源是拆分前提交 `aaf038c` 保存的本地 Web 代码，不代表在线网站的最新状态。Godot 当前玩法来自同一提交的已验证原生实现；此轮只拆分工程和验证流程，没有重新设计玩法。

| 方面 | 对照 Web 版 | 当前 Godot 版 |
| --- | --- | --- |
| 运行 | 浏览器 JavaScript / Three.js / WebGL，Next.js 页面承载游戏 | 原生 GDScript、Godot 场景、Forward+ / Metal 或兼容渲染 |
| 内容来源 | 角色、地图、材料与音乐可由 JS 过程代码生成 | 模型、动画采样、贴图、地图、导航、小地图、音频已在本地资源中；不执行 JS |
| 权威 | Web 自己的配置与模拟 | 本地配置经过 Godot 平衡与装备扩展，玩法只由当前 Godot 规则决定 |
| 联机 | Web 存在浏览器直连／WebRTC、WSS 与局域网服务 | 当前原生版是单机玩家＋机器人，未移植这些联机协议；5v5 不代表十名在线玩家 |
| 配装 | 基础可选四主武器：喷枪、滚筒、狙、爆破枪 | 八主武器，增加双持、飞镖、墨弓、挡墨伞；九道具、八天赋，以当前选择池为准 |
| 地图 | 潮水／海带两种几何布局，另有复用潮水布局的黄昏主题 | 七张可选地图，十九套预生成布局／模块组合；不表示任意运行时生成地形 |
| 生命／基础伤害 | 默认 100 HP、喷枪基础 36、满蓄狙 160 | 均衡默认 120 HP、喷枪近端 30、满蓄狙 100；实际伤害仍受距离、部位、天赋、护盾与封顶规则影响 |
| 复活 | 基础复活时间 5.5 秒，原版自己的出生／跳跃机制 | 基础 4 秒，玩家主动选择基地、队友或信标；排队／取消／落点失效按本地部署规则 |
| 结算 | finish 暂停后进入 judge 展示 | finish 2.6 秒后直接 results，显示最终地图、比例与分队战绩 |
| UI | Web DOM / CSS 菜单与 HUD | 原生 Control / CanvasLayer，同页配装、3D 地图／人物预览、响应式 HUD 与 Tab 战术图 |
| 墨迹和战绩 | Web 的墨面／计分实现 | CPU 墨格是覆盖率和累计涂地的权威；墨迹材质、小地图、HUD 只读这些状态 |
| 资源检查 | JS 转换器对照 Web 源码与输出哈希 | 本地 `assets/integrity.json` 检查内容、体积与完整清单；规则／场景检查验证语义 |
| 构建 | 网页构建与服务器发布 | Godot arm64 `.app`；当前工程拆分没有重新导出或公开发布新包 |

以上伤害／时间是本次基线举例，后续平衡以实际 Godot 代码、数据、测试和玩法文档为准。禁止为追求“忠实移植”直接恢复 Web 数值。已退出选择池的 heavy、rapid、旧恢复／护盾道具和部分旧天赋数据是兼容记录，不表示它们仍可选。

角色身体、脸部、骨骼、服装、地图材料、字体和音频延续已有美术资产，资产历史与许可证保留。移除网页代码不意味着替换外观、删模型或重新生成音频。新武器／道具／天赋的具体操作见 [GAMEPLAY.md](GAMEPLAY.md) 和 [CREATIVE_LOADOUTS.md](CREATIVE_LOADOUTS.md)。

## 2. 当前维护依据

| 维护内容 | 当前入口／权威 |
| --- | --- |
| 基础参数 | `assets/weapons.json`，作为本地导入基线；仍包含历史来源字段 |
| 生效的平衡与装备 | `src/core/gameplay_rules.gd` 叠加基础参数，再调用 `equipment_catalog.gd` 扩展；武器／能力模块消费最终数据 |
| 菜单选择池 | `equipment_catalog.ACTIVE`、`tidewater_items.KINDS`、`tidewater_perks.ORDER`、`map_catalog` |
| 对局阶段／生命／伤害／累计账本 | `src/match/tidewater_play.gd` 与对应 combat／abilities 模块 |
| 地图几何与导航 | `assets/maps/` 的碰撞／墨面／导航／小地图数据及 `src/world/` 读取器 |
| 归属与最终覆盖率 | `src/world/surface_ink.gd`，最终覆盖率与个人累计新占面积是不同指标 |
| 显示 | `surface_ink_view.gd`、角色 visual、UI 与 presentation，只消费权威状态 |
| 外部来源说明 | `THIRD_PARTY_NOTICES.md`、`licenses/`、现有资源的 provenance 字段 |
| 内容完整性 | `assets/integrity.json`；它不取代玩法／碰撞／动画等语义验证 |

旧生成器已经移除。更改本地资产可以使用 Godot 编辑器、明确的本地建模／绘图工具或新的原生资源工具；新的生成流程必须进入 `tools/`，具有明确输入、输出和检查，不能悄悄读旧 Web 仓库。地图与动画的完整原生生成器尚未另行实现，当前保留的是已验证的输出资源。

## 3. AI 每次开始工作

1. 读根目录 `AGENTS.md`、本文件与 [COORDINATION.md](COORDINATION.md)，检查 `git status`、分支／HEAD 和已有未提交修改。
2. 根据 [STRUCTURE.md](STRUCTURE.md) 找所属模块，阅读对应调用者和检查；列出本次目标、边界与完成条件。
3. 一次推进一项任务。用户要求“先别实现／只给方案”时仅检查并提出方案；用户授权实现后执行可验证的小批次。
4. 当前项目只维护 Godot。不要修改旧 Web 仓库，不自动恢复 JS 工具，不把旧源码／截图／发布包当当前证据，不以绝对路径读取别的项目。

## 4. 不可破坏的运行规则

- 只有 CPU 墨格负责涂地归属、有效面积与计分；颜色只是显示，不能通过 RGB 推断队伍或让两个消费者互相清除脏格。
- 对局控制器只保留一份玩法状态。HUD／菜单不能复制生命、墨量、覆盖率或额外创建伤害账本。
- 当前阶段为 home → setup → intro → playing → finish → results。改变阶段要同步输入、声音、HUD、结算、检查和玩法文档。
- 玩家必须主动选择复活地点；不得静默自动选择队友／信标。道具冷却跨死亡和重摇保留，天赋开战锁定整局。
- 按实际三维距离、墙／楼板遮挡和观察结果判定命中、情报、部署与机器人行为。不要让机器人或小地图透墙获取未发现敌人的实时位置。
- 主武器的生命伤害、护盾吸收、溢出、归属与充能必须走同一权威路径；共享单轮预算的武器不能拆成多次绕过封顶。
- 更改玩家配置要初始化传给子 visual 和机器人；不能依赖子节点 `_ready()` 早于父配置。使用非默认注入值验证消费者实际生效。
- 保持 UI 隐藏状态、信号生命周期和资源复用；布局随窗口／设置变化更新，每帧只刷新实时值。
- 不未经用户确认替换正式人物外观或把被否决的 `experiments/` 样板接入默认场景。

## 5. 文件与资源变更规范

1. 玩法脚本放对应 `src/` 模块；场景、着色器、资产、检查、工具和文档分目录。不要把所有新增文件堆在根目录，不为小改动扩散跨层依赖。
2. 移动 GDScript／着色器时一起移动 `.uid`，保持 UID；检查 preload、场景、材质、工具、测试和文档引用。不要手工改 `.godot/` 导入缓存或删除其他任务的修改。
3. 改地图须同步碰撞、可涂／计分面、导航、布景与小地图；检查双方出生区、高低层通行、视线／薄楼板和所有受影响的变体。视觉布景不得重复建立碰撞。
4. 修改模型／动作／材质要验证骨骼、两队颜色、各武器持握、形态与必要动作；音频要验证阶段、暂停／恢复和音量行为。
5. 资源基线更新顺序：相关语义检查／预览 → 确认有意变化 → `python3 tools/update_asset_integrity.py --write` → 审查清单 diff → 统一检查。不得先批量刷新哈希来隐藏异常。
6. provenance 中旧 JS 路径／散列仅记录历史；当前不能打开这些路径作为依赖，也不能重写旧对局数据中的源码哈希伪造新验收。
7. `.godot/`、`build/` 和缓存不提交；证据进入新命名的 `render-evidence/` 子目录，保留 `.gdignore`，避免覆盖历史图像和报告。保留合法来源与字体许可。

## 6. 验证顺序与证据

默认入口：`./tools/run_checks.sh`。导入后先检查生产脚本编译，再检查本地资源完整性，任何失败都停止后续场景检查。编译依据 `GDScript.reload() != OK`，不是只判断 `load()` 是否非空；空源码清单不能通过。默认单项超时 120 秒，不能随意缩短物理帧等待的地图检查。

按变更运行以下隔离检查，不要求每次无意义重复全部检查：

- 编译／入口变更：`python3 tests/python/test_parse_gate.py`，故意坏脚本、坏依赖及两道门的失败阻断。
- 资源门变更：`python3 tests/python/test_asset_integrity.py`，损坏、缺失、新增、空清单与导入元数据排除。
- 启动／导入变更：`python3 tests/python/test_runtime.py`。
- 参数初始化变更：`python3 tests/python/test_visual_config.py`，包括 `runSpeed=6` 和注入 `12`。
- 界面／渲染变更：原生运行受影响场景，记录 Forward+ / Metal 或兼容模式、窗口、UI 比例和输入方式。不能用 headless 截图替代原生画面。

报告须区分：编译／静态检查、无界面规则、受控原生截图／自动输入、自然对局、真人试玩、帧时间／温度、实际导出包。自动缩短计时、移动角色、设置生命或强制结算的场景只算受控检查；107 或其他历史数量不代表完整手感、温度或联网已经验收。

已通过且没有新修改／新疑点时，不反复扩大验证。测试要覆盖有意义的失败模式，不只复述实现。
